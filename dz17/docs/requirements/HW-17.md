# HW-17: SENTRY SWM-2 Acceptance Testing

**Required equipment and files:** ESP32-S3 DevKit with an HC-SR04 sensor, relay, diode, and buttons; `sentry_fw7_v2.1.0_merged.bin` from this folder; a 2.4 GHz Wi-Fi network with Internet access; and a serial terminal configured for 115200 baud.

**Submission format:** `HW-17_<LastName>.zip` containing `REPORT.md` and a `logs/` directory.

The requirements are defined in `PRD.md`. Test strictly against the PRD. Features specified in the PRD as available **starting with version 2.3.0** must not be reported as defects in version 2.1.0.

---

## Tasks

1. **Flash firmware version 2.1.0** (see `README.md`), then execute `connect`, `register`, and `login`.
2. **Test version 2.1.0 against the entire PRD:** Wi-Fi, user accounts, operating states, OTA, lamp, relay, sensor, health monitoring, and buttons. Include boundary-value tests (minimum, maximum, one below the minimum, and one above the maximum), as well as behavior after a reboot.
3. **Perform an OTA update:** Run `ota update beta` to upgrade to version 2.3.0. Verify data persistence (PRD requirement OTA-10).
4. **Test version 2.3.0:** Verify new functionality (Guard, Alert Center, K4), then repeat all tests performed on version 2.1.0 (regression testing).
5. **Test OTA scenarios:** `ota broken` (rollback), `ota install 2.1.0` both with and without `force`, and `ota update` when the device is already running the latest version.
6. **Test OTA failure scenarios using the local server** (see `tools/README.md`): interrupted downloads (`--drop-at`), slow downloads combined with Wi-Fi disconnection (`--slow`), `garbage.bin`, `truncated.bin`, and `corrupted.bin`. After each failure, verify that the device remains operational and that a subsequent OTA update succeeds. Remember to restore the default OTA server with `ota server default` at the end.
7. **Exploratory testing (bonus):** The firmware contains hidden commands and secrets. Document everything you discover and assess the security implications.

Verify physical behavior (LED, diode, and relay) through direct observation, not solely through log output.

---

## Required Contents of `REPORT.md`

**1. Test checklist** — For each firmware version, include the test or verification item, the corresponding PRD requirement, and the result (PASS / FAIL with defect ID).

**2. Defect reports** — For each defect, include:

- Defect ID and title
- Firmware version in which the defect was discovered and whether it is reproducible in the other version
- Severity and priority
- Preconditions and steps to reproduce
- Expected result (with the relevant PRD requirement)
- Actual result
- Evidence: log excerpt, photograph, or video
- Reproducibility (e.g., 3/3 attempts)

**3. Defect matrix** — Indicate which defects are present in versions 2.1.0 and 2.3.0. Identify regressions separately (defects that were previously fixed but have reappeared).

**4. Security findings** (if any).

**5. Conclusion** — State whether version 2.3.0 can be promoted from beta to stable, with a brief justification.

The `logs/` directory must contain logs of OTA transitions and evidence reproducing each defect.

Do not include your Wi-Fi password in submitted logs; redact it as `***`.
